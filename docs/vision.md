# Видение hex-canvas-mobile

Короткий манифест: что строим, для кого, на каких принципах. Не бэклог и не дневник — рамка, внутри которой принимаются все остальные решения. Если очередная фича не ложится в манифест — либо манифест стар, либо фича лишняя.

## Что это

Personal knowledge management для одного оператора (автора проекта), развёрнутый как Android-приложение с ветвящимся чатом на гекс-канве. Отличается от записной книжки, чат-клиента и PKM типа Obsidian тем, что **LLM сидит в центре, а канва вокруг него** — не «чат как фича», а «канва как память чата и среда работы соавтора».

## Для кого

**Оператор — один человек, автор.** Не продукт для рынка. Решения, которые бы нужны массе пользователей (миграции, оппции разной сложности, локализация), но мешают оператору, отсекаются.

**Соавтор — LLM (сейчас я, Claude через туннель).** Читает состояние через `/screen`, меняет через `/action`, помнит через git (`PASSPORT.md`, `cases/`, `CLAUDE.md`), думает в этом контексте.

## Принципы

1. **Кирпичи, а не продукты.** Если что-то повторяется 3+ раза — становится переиспользуемой единицей (ScreenSnapshotProvider, llm_client, compress_sheet). Одиночные use-case'ы остаются inline, не стандартизуются зря.

2. **Сквозные слои, а не точечные фичи.** ВР (время) пронизывает timestamps, session tracker, bubble time, напоминания, system prompt. ПМ (память) — следующий слой. Каждый новый концепт сперва проверяется «это слой или локальная фича».

3. **Спека-как-источник.** Решения описываются до реализации (PASSPORT бэклог-пункт, кейс-заметка, ДЛ-пакет). Код без спеки — риск разойтись с намерением.

4. **Кейсы — память причинности.** `cases/NNN-slug.md` — отдельные истории ретроспективы: что открыло, что закрыло бы A. Не «что сделали», а «почему именно так».

5. **Delegation artifacts (ДЛ).** Пакет работы, который соавтор выполняет без уточнений: цель, acceptance, out-of-scope, ресурсы. Позволяет делегировать разным исполнителям (я, Cursor, фрилансер) и работать в режиме «оператор не на связи».

6. **Две стадии подъёма.** Часто первая реализация (createdAt на ноде) даёт данные, а с её высоты виден потолок (LLM слепа во времени) и нужный кирпич (сквозной слой ВР). Не чинить отсутствующее — замечать что появилось после первого шага.

## Режимы оператора (см. [cases/003](../cases/003-rezhim-operatora.md))

- **Ночь у ПК**: короткие команды, оператор жмёт код. Для кодинга, рефакторинга, крупных шагов.
- **День в цеху**: мысли редко, но длинные. Для рамок, кейсов, ДЛ-пакетов, не для кода.

Соавтор подстраивается под режим оператора, не наоборот.

## Чего НЕ строим

- **Не продукт для рынка.** Никакой онбординг, никакая поддержка legacy-пользователей.
- **Не универсальный IDE.** Мастерская — песочница, но не платформа плагинов.
- **Не оффлайн-LLM как default.** Облачные модели пока основа; локальный Ollama — опциональный путь для чувствительного (КФ3).
- **Не real-time collaborative edit.** Один оператор, один устройство, git как единственная синхронизация.
- **Не backup-сервис.** Дампы (`inbox/*.md`) — для внешней обработки, не для бекапа канвы.

## Сквозные слои

- **ВР — время:** timestamps везде, session context в system prompt, bubble time с относительным age, напоминания, ретроспективы.
- **ПМ — память:** persistent memory between sessions, digest, RAG по дампам и кейсам. Стройится на ВР.
- **ДЛ — делегирование:** формат пакета работы.
- **СП — спека-первым:** каждое изменение сначала в формате (бэклог/кейс/delegation), потом код.
- **ОТ — отладочный API:** `/state`, `/screen`, `/action/*` — туннель в мобильник для внешнего соавтора.

## Текущее состояние (2026-04-18)

- Чат с ветвлением, канва гексагональная, LLM через единый клиент (Р2).
- Мастерская: веб-поиск (агент с 4 tools + fetch_rss), режим тезисов, напоминания (ВР4), инбокс, дерево решений, кейсы, отладка, разработки.
- Отладочный API `/screen` + actions (ui.navigate, chat.addNote, canvas.undo/redo) — внешний соавтор «видит» и «постит».
- ВР-минимум везде в system prompt. ПМ и ДЛ — в планах.

## Как это читать дальше

Манифест короткий намеренно. Детали в `PASSPORT.md` (backlog + протокол), в `cases/` (истории решений), в `docs/ops/` (операционные инструкции). Если что-то в коде не согласуется с манифестом — либо обновляем манифест, либо код.
